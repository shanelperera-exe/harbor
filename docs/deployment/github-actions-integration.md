# GitHub Actions deployment integration

Harbor triggers a repository's `workflow_dispatch` event when a deployment is
created. The workflow file is stored in each target repository (default:
`deploy.yml`). Harbor does not build, test, or deploy the service itself; it
only creates a deployment record, calls the GitHub Actions API, and optionally
receives status callbacks from the workflow.

One GitHub App handles both Harbor user login (user access token) and
deployments (installation access token). See the [GitHub App setup guide](#)
for registration instructions.

## How the integration works

When Harbor creates a deployment, it resolves a **GitHub App installation
token** for the user who triggered the deployment, then reads the service's
GitHub repository as `owner/repository`, selects the configured workflow file
and ref, and calls:

```text
POST {GITHUB_API_BASE_URL}repos/{owner}/{repository}/actions/workflows/{workflow-file}/dispatches
Authorization: Bearer {INSTALLATION_TOKEN}
```

The installation token is created from the GitHub App's JWT and the user's
installation ID, then cached for up to 45 minutes. The request body contains a
`ref` and the following case-sensitive inputs:

| Input | Value |
|---|---|
| `environment` | Harbor environment name |
| `project` | Harbor project id |
| `service` | Harbor service id |
| `deployment_id` | Harbor's internal numeric deployment id |
| `version` | Selected version |
| `commit_sha` | Selected commit, or an empty string |

Harbor uses the commit SHA as the workflow ref when one is selected; otherwise
it uses the service branch. A successful trigger changes the Harbor deployment
to `Running`. GitHub then executes the workflow.

## Repository prerequisites

1. The repository must be accessible to the GitHub App installation that the
   Harbor user has authorized.
2. The workflow must exist at `.github/workflows/<workflow-file>` on the ref
   that Harbor dispatches.
3. The workflow must declare `on: workflow_dispatch` and define all six inputs
   above. Input names are case-sensitive.
4. The workflow must check out the requested ref and implement build, test, and
   deployment steps.
5. The GitHub App needs Actions write access and repository contents read
   access. These permissions are configured on the GitHub App itself, not per
   token.
6. Keep cloud, registry, and environment credentials in GitHub Actions secrets
   or variables. Do not put them in Harbor requests, source code, or workflow
   input values.

## Configure the Harbor deployment service

These variables belong to the **Harbor.Deployment service process or container**.
They are separate from the environment variables configured for an application
service in the Harbor UI.

```dotenv
# GitHub App credentials (all services, from .env)
GITHUB_APP_ID=
GITHUB_APP_CLIENT_ID=
GITHUB_APP_CLIENT_SECRET=
GITHUB_APP_PRIVATE_KEY_BASE64=
GITHUB_APP_SLUG=
GITHUB_APP_WEBHOOK_SECRET=
GITHUB_API_BASE_URL=https://api.github.com/

# Harbor deployment status callback (separate from GitHub App webhook secret)
GITHUB_WEBHOOK_SECRET=
GITHUB_ACTIONS_WORKFLOW=deploy.yml
```

### GitHub App credentials

The deployment service uses the GitHub App credentials to generate an
installation JWT and create short-lived installation tokens for workflow
dispatches. Each service reads the same `GITHUB_APP_*` values from its
environment.

| Variable | Source in GitHub | Description |
|---|---|---|
| `GITHUB_APP_ID` | App settings → App ID | Numeric app identifier |
| `GITHUB_APP_CLIENT_ID` | App credentials → Client ID | OAuth client ID (GitHub App, not OAuth App) |
| `GITHUB_APP_PRIVATE_KEY_BASE64` | App settings → Private keys | Base64-encoded PEM private key |
| `GITHUB_APP_SLUG` | App settings → App slug | URL-friendly app name |
| `GITHUB_APP_WEBHOOK_SECRET` | App settings → Webhook secret | HMAC secret for GitHub App webhook verification |

Store the private key as a secret, never as a plaintext variable.

### `GITHUB_WEBHOOK_SECRET`

This is a shared secret for the optional workflow-to-Harbor status callback. It
is not generated by GitHub and is not a GitHub App webhook secret.

Generate a strong value locally, for example:

```bash
openssl rand -hex 32
```

Configure the exact same value in both places:

- Harbor deployment service environment variable:
  `GITHUB_WEBHOOK_SECRET`
- GitHub Actions repository or environment secret, for example:
  `HARBOR_WEBHOOK_SECRET`

The variable names may differ between the two systems, but the values must
match. If this secret is omitted, Harbor accepts no status callbacks and a
successfully triggered deployment remains `Running`.

### `GITHUB_ACTIONS_WORKFLOW`

Set this to the exact workflow filename in the target repository, including
case. The default is `deploy.yml`.

```text
.github/workflows/deploy.yml
```

Do not include the `.github/workflows/` directory in this variable. A service
may override the default with its own workflow filename.

### `GITHUB_API_BASE_URL`

This is the GitHub REST API base URL, not the Harbor API URL.

- GitHub.com: `https://api.github.com/`
- GitHub Enterprise Server: `https://<host>/api/v3/`

Keep the trailing slash. The default is `https://api.github.com/`.

For local Docker Compose development, the deployment service loads the root
`.env` file through `env_file` in `docker-compose.yml`. The template is
`.env.example`; never commit real token or secret values. In a production
deployment, set these values through the platform's environment or secret
configuration and restart the service after changing them.

## Example workflow

The following workflow declares the required inputs, checks out the requested
ref, runs the deployment script, and reports the final status back to Harbor.

```yaml
name: Deploy
on:
  workflow_dispatch:
    inputs:
      environment: { required: true, type: string }
      project: { required: true, type: string }
      service: { required: true, type: string }
      deployment_id: { required: true, type: string }
      version: { required: true, type: string }
      commit_sha: { required: false, type: string }

permissions:
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ inputs.commit_sha || inputs.version }}

      - name: Deploy
        run: ./scripts/deploy.sh

      - name: Report deployment result
        if: always()
        env:
          HARBOR_API_BASE_URL: ${{ vars.HARBOR_API_BASE_URL }}
          HARBOR_WEBHOOK_SECRET: ${{ secrets.HARBOR_WEBHOOK_SECRET }}
        run: |
          if [ "${{ job.status }}" = "success" ]; then
            status="Succeeded"
          else
            status="Failed"
          fi

          body="{\"status\":\"$status\"}"
          signature=$(printf '%s' "$body" | openssl dgst -sha256 -hmac "$HARBOR_WEBHOOK_SECRET" -hex | cut -d' ' -f2)

          curl --fail-with-body -sS -X POST \
            "${HARBOR_API_BASE_URL%/}/api/deployments/${{ inputs.deployment_id }}/status" \
            -H "Content-Type: application/json" \
            -H "X-Harbor-Signature: $signature" \
            --data-binary "$body"
```

`HARBOR_API_BASE_URL` is a GitHub Actions variable containing the publicly
reachable Harbor API base URL, such as `https://harbor.example.com`. It is not
one of Harbor's deployment-service variables above. Use the URL of the API
gateway or deployment service that GitHub runners can reach; `localhost` only
works when the callback originates on the same host.

The `environment` input can select a GitHub environment, which allows
environment-specific secrets and protection rules. Store cloud credentials and
registry tokens as repository or environment secrets, not as Harbor deployment
inputs.

The `version` value must be a valid Git ref (branch, tag, or commit) if it is
used as the checkout ref. If it is an application version such as `1.2.3`,
resolve it to a branch, tag, or commit in the workflow before checking out.

## Status callback contract

The optional callback endpoint is:

```text
POST /api/deployments/{deploymentId}/status
```

`deploymentId` is the internal numeric value sent in the `deployment_id` input,
not the public deployment identifier shown in the Harbor UI.

Send a JSON body with one of these statuses:

```json
{"status":"Running"}
```

```json
{"status":"Succeeded"}
```

```json
{"status":"Failed"}
```

Set `X-Harbor-Signature` to the lowercase hexadecimal HMAC-SHA256 digest of the
exact JSON body bytes, using `GITHUB_WEBHOOK_SECRET` as the HMAC key. Do not add
a `sha256=` prefix, reformat the JSON, or add a trailing newline after
calculating the signature.

The callback route is intentionally available without a Harbor user JWT, but
the HMAC check is mandatory. If the Harbor secret is missing, the endpoint
returns `401 Unauthorized`.

A workflow may report `Running` before a long deployment and report
`Succeeded` or `Failed` in an `if: always()` step at the end. The final callback
is what allows Harbor to show completion and failure reasons.

## Configuration checklist

- [ ] One GitHub App is registered with the correct callback and webhook URLs.
- [ ] The GitHub App has **Repository Actions: Read and write** and
      **Repository contents: Read-only** permissions.
- [ ] The GitHub App subscribes to `installation` and
      `installation_repositories` webhook events.
- [ ] All `GITHUB_APP_*` variables are set in the Harbor deployment service
      environment or secret manager.
- [ ] The target repository is accessible to the GitHub App installation that
      the Harbor user authorized.
- [ ] `.github/workflows/deploy.yml` exists on the dispatched ref.
- [ ] The workflow declares all six exact input names.
- [ ] `GITHUB_ACTIONS_WORKFLOW` matches the workflow filename.
- [ ] `GITHUB_API_BASE_URL` points to GitHub's API, with a trailing slash.
- [ ] Any callback secret is configured in both Harbor and GitHub Actions.
- [ ] `HARBOR_API_BASE_URL` in GitHub Actions points to a publicly reachable
      Harbor API endpoint.
- [ ] Cloud and registry credentials are GitHub secrets or variables.
- [ ] The workflow checks out the requested ref and performs build, test, and
      deployment steps.

## Troubleshooting

| Symptom | Likely cause | Check |
|---|---|---|
| Harbor reports no GitHub login option | GitHub App credentials missing | Verify `GITHUB_APP_CLIENT_ID` and `GITHUB_APP_CLIENT_SECRET` are set |
| Harbor reports installation token error | GitHub App private key missing or invalid | Verify `GITHUB_APP_PRIVATE_KEY_BASE64` is correct and not expired |
| Harbor reports `No GitHub App installation found` | User hasn't installed the app | Have the user log in and install the GitHub App on their account/org |
| GitHub returns `401` or `403` | App lacks permissions or installation lacks repo access | Check GitHub App permissions and installation repository selection |
| GitHub returns `404` | Wrong owner/repository, workflow filename, or ref | Check the service repository value and the workflow path on the dispatched branch or commit |
| Workflow does not appear in GitHub | Workflow was not committed to the dispatched ref | Commit the workflow to the target branch and rerun the deployment |
| Harbor remains `Running` | The workflow did not call the callback or the callback failed | Check the GitHub Actions run logs and Harbor deployment-service logs |
| Callback returns `401` | Secret mismatch, missing Harbor secret, or signature calculated over different bytes | Compare both secret values and sign the exact body sent by `curl` |
| Callback returns `404` | Wrong Harbor base URL or wrong deployment id | Use the public Harbor API URL and the numeric `deployment_id` input |
| Checkout fails | `version` is not a Git ref | Use a branch, tag, or commit SHA, or resolve the application version first |
